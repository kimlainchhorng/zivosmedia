# Autorepair print/QR builders — stored-XSS hardening (cross-repo)

**Date:** 2026-06-15
**Scope:** zivosmedia + zivosoftware (shared autorepair admin module)
**Class:** Stored XSS via unescaped free-text in print/share HTML builders
**Status:** Done — 12 files across 2 repos + 1 shared helper per repo. Typecheck green in both.

## The bug class

The autorepair admin has several "print" / "share" / "QR" actions (Build R.O., Estimate,
Customer envelope, Carfax/vehicle, RO status, Tech assignment, Booking-link QR). Each one
assembles a **standalone HTML document as a string**, interpolating repair-order and
customer free-text fields, then hands it to `document.write(html)` or
`printOrShareHtml(html, ...)`.

The print popup is opened with `window.open("", "_blank")` → an **about:blank** document
that is **same-origin** with the app. So an unescaped `<img onerror=...>` (or `<script>`,
`<svg onload>`, etc.) sitting in stored shop data executes as **same-origin JavaScript**
in the print window — with access to `window.opener` (the live admin session).

This matters because some of these free-text fields can originate from the
**customer-facing booking link / estimate-approval flow** (customer name, email, phone,
vehicle, notes). That makes it a genuine **stored-XSS → staff-session** path, not just
self-XSS.

## The fix

A single shared helper per repo:

```ts
// src/lib/escapeHtml.ts
export function escapeHtml(value: unknown): string {
  return String(value ?? "")
    .replace(/&/g, "&amp;")   // & first, so later entities aren't double-escaped
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;");
}
```

Applied around **every free-text data interpolation** in the HTML builders. The escaping is
additive and lossless for display: it only ever neutralizes markup, never changes the
visible text.

### What is escaped (free-text, attacker-influenceable)
- Customer: name, email, cell/work phone, street/city/state/zip (envelope)
- Vehicle: label, VIN, plate, mileage
- RO: number, technician, status, ETA text, line-item description + misc, notes/concerns
- Estimate: number, customer name/phone/email, vehicle label, item kind/name, notes
- Booking QR: the booking URL line

### What is deliberately NOT escaped (not a sink)
- **Numerics / money / dates** — `money(...)`, `l.qty`, `.toFixed(...)`, timestamps. These
  are generated by the app from numbers, never contain markup.
- **Static template chrome** — the literal `<style>`, headings, table scaffolding.
- **Base64 image data URLs** — `canvas.toDataURL("image/png")` for the QR `<img src>`; this
  is app-generated base64, not free text.
- **`printOrShareHtml` title argument** — e.g. `Print RO ${header.number}`. That string is a
  native share-sheet/document title, not interpolated into the HTML document, so it is not
  an HTML sink.

## Related fix — JSON-LD `</script>` breakout (zivosmedia only)

`src/components/seo/FlightReservationSchema.tsx` rendered structured data with
`dangerouslySetInnerHTML={{ __html: JSON.stringify(schema) }}`, where `schema` embeds
user fields (`passengerName`, `bookingReference`, `airline`). `JSON.stringify` does **not**
escape `<`/`>`/`&`, so a value containing `</script>` could break out of the JSON-LD
`<script>` and inject markup.

Fix: escape the three HTML-significant characters as JSON unicode escapes after
serialization —
```ts
const json = JSON.stringify(schema)
  .replace(/</g, "\\u003c").replace(/>/g, "\\u003e").replace(/&/g, "\\u0026");
```
`<` etc. are valid JSON string escapes, so the JSON-LD parser still reads the original
characters — the structured data is unchanged, but the raw `<script>` text can no longer
contain a literal `</script>`.

Audited the sibling JSON-LD sites: the `<script type="application/ld+json">{JSON.stringify(...)}</script>`
JSX form (PublicCarRentalBookingPage, HotelsLandingPage, ZivoTravelHome, CheapFlightsGuide)
renders via React **text nodes** (`textContent`), which are not HTML-parsed, so they are not
breakout sinks. Only the `dangerouslySetInnerHTML` form was vulnerable. No sibling repo has
the `dangerouslySetInnerHTML`+`JSON.stringify` pattern.

Other `innerHTML`/`dangerouslySetInnerHTML` sites reviewed and cleared:
- `main.tsx` boot-error painter — already escapes `[&<>]` inline.
- `HotelsMapView.tsx` price pill — numeric-derived `formatPrice`; name via `setAttribute`.
- `StoreMapPage.tsx` marker fallback — only interpolates `selected ? 20 : 16`.
- `TwoFactorSetupDialog.tsx` QR — Supabase-generated QR matrix (no user text in markup).
- `ui/chart.tsx` — standard shadcn; developer-supplied theme colors, not user data.

## Post-fix attribute-context audit (DeepSeek-guided)

A second-opinion review (DeepSeek, security role) confirmed `&<>"'` escaping is sufficient
for the two contexts the builders actually use — HTML **text** and **double-quoted, non-URL/
non-CSS/non-event** attributes — and that the base64 QR `dataUrl` and `document.write`-into-
about:blank sink introduce no additional gap (no mXSS: the sink is the HTML parser, not
`innerHTML` re-serialization). It flagged one thing to verify empirically: that no free-text
ever lands in a URL (`href`/`src`), `style`, or `on*` attribute.

Grepped both repos' autorepair trees for `(href|src|style|on*)="${...}"`. Result: every hit is
either live-app **JSX** (React-escaped, not a print sink) or safe. Inside the actual
`document.write` / `printOrShareHtml` strings the only URL-attribute interpolations are:
- the QR `<img src="${dataUrl}">` — canvas `toDataURL` base64 `[A-Za-z0-9+/=]`, safe;
- the booking embed snippet `<script src="${window.location.origin}/widget.js" data-store="${storeId}">` —
  own origin + system UUID, and it is clipboard/display text, **not** a print sink.
No free-text field reaches a URL/CSS/event-handler attribute. Escaping is sufficient.
