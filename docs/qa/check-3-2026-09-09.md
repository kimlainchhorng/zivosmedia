## Realtime changes

The old connection guard could drop a retry arriving before its deadline and leave the notice stuck at Reconnecting. The circuit now owns its retry timer, waits for disconnect completion, caps five failed attempts, preserves the failure budget across routes, and resets only on explicit Retry or acknowledged protocol work. Intentional disconnects clear obsolete notices. An installed-SDK transport fixture exercises the actual timers rather than manually driving every attempt.

Static landing, Flights/Hotels search, careers, contact/about, legal and auth routes pause the shared WebSocket transport and hide the live notice. Registered subscriptions resume when returning to a live workflow; live chat, wallet and order/booking routes remain eligible. Route changes cannot reset an exhausted budget. The singleton clients remain available for ordinary REST requests; constructing them does not open a socket.

The active five-minute monitor now uses protocol **2.0.0**, including binary JSON broadcast decoding. The browser QA uses the installed SDK plus the application circuit. Health still requires a nonce round-trip, not merely a 401 response. The keyed plain-HTTP 1101 is tracked in the support request and is not misreported as proof that WebSocket transport is down.

## Wallet changes

Card reads and payment changes now have separate persistent limits keyed to the authenticated user: **60 reads/minute**, **10 changes/minute**, plus the existing broad IP abuse guard. All reads require server-verified authentication. A rollback-only production database fixture confirmed 15 normal reads are allowed and mutation 11 is denied; it saved no limiter records. Ordinary list reads no longer create Stripe customers.

The card hook caches successful results in memory per user/auth session, deduplicates mounts, disables background focus/reconnect refetches and invalidates after a card change. Reads retry at most twice with exponential delay and Retry-After handling. `retryOnMount: false` prevents route remounts from restarting an exhausted sequence; the regression test reproduced six calls before the fix and verifies three afterward. 429 and legacy 403/Too-many-requests receive a cooldown state; genuine 401/403 denials do not auto-retry and hide previously loaded card data. Account/session keys and abort signals fence held responses across account changes. No card cache is written to browser storage.

The wallet retains its header/tabs and displays a friendly EN/KM card-read recovery panel. A separate route error boundary retains a Wallet heading and Retry without rendering exception bodies. Provider messages are classified internally and never used as UI copy.

The website Worker had a separate path to a raw JSON document: every JavaScript/font download consumed the 600-request site bucket, and exceeding it returned JSON even for a wallet page navigation. Build assets now bypass that page/API bucket; API and page limits remain enforced. Throttled document requests receive an EN/KM HTTP 429 page with Wallet/ZIVO navigation and Retry, no-store and Retry-After headers. API requests retain JSON errors. A Worker integration fixture verifies 650 build downloads do not exhaust navigation allowance, while repeated API calls still reach HTTP 429. This is an additional reproduced code path, not proof that it caused the owner's exact screenshot.

Mobile browser fault injection also caught the consent banner opening on pointer-down and covering Retry before click completion. The banner now waits for click/key-up; the original action completes before it appears. Consent is still required before analytics/marketing activation.

The list response returns only card ID, brand, last four digits, expiration and default status. Removed customer_id; removed raw Stripe exception text and verbose identity/provider logging. SetupIntent responses retain only the scoped client_secret required by Elements. Existing card-ownership checks are preserved and now also present in the deployed function. No full card number, CVC, billing contact or customer object is returned by the list action.
